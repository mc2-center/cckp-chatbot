# Fix portal redirect URLs: wrong Detail Page pattern + broken collection search

## Context

The user reported that agent-generated portal redirects aren't showing expected results. Live-testing against `staging.cancercomplexity.synapse.org` (via browser automation) confirmed two distinct, previously-unverified bugs — everything in this plan is grounded in actual observed portal behavior, not assumption:

**Bug 1 — Detail Page links use a URL shape that doesn't exist.** The agent's current instructions (`agents/cckp-copilot/cloudformation.sql.yaml`, "Resource Detail Page Links" section, added earlier this session from unverified guidance) generate e.g. `/Explore/Datasets/DetailsPage?datasetId=syn77068011`. Navigating to that live: **blank white page.** Reading real hrefs off actual rendered result cards shows the true pattern is a plain path segment, no "DetailsPage", no query string:

| Resource | Real pattern (confirmed live) |
|---|---|
| Datasets | `/Explore/Datasets/{datasetId}` (synId, e.g. `syn77068011`) |
| Publications | `/Explore/Publications/{pubMedId}` (e.g. `42151118`) |
| Tools | `/Explore/Tools/{toolName}` (e.g. `Pycashier`) |
| Grants | `/Explore/Grants/{grantId}` (a synId, e.g. `syn9775689` — **not** `grantNumber`) |
| Educational Resources | `/Explore/Educational Resources/{title}` (`%20` for spaces in the title; note the *collection* path itself also has a literal space — confirmed via the site's own nav tab `href="/Explore/Educational Resources"`, not `EducationalResources` as currently instructed) |

Also confirmed: the portal's own rendered "LINK" field for a raw Synapse entity uses `https://www.synapse.org/#!Synapse:{id}` (legacy hash-route), not the `https://www.synapse.org/Synapse:{id}` form currently in the raw-Synapse-fallback rule.

**Bug 2 — Collection-page filtered search needs a `qw0` (gzip+base64+urlencoded) query param, not raw JSON.** Decoded a real captured `qw0` value: it's `urlencode(base64(gzip(json)))` of `{"sql", "includeEntityEtag", "isConsistent", "additionalFilters", ...}`. Confirmed live, in this order:
1. `/Explore/Datasets` (no trailing slash) + any query string → 301-redirects to `/Explore/Datasets/`, **query string dropped entirely** (loads all 1,141 datasets, unfiltered).
2. `/Explore/Datasets/` (trailing slash) + the real `qw0` → correctly shows 37 filtered results.
3. `/Explore/Datasets/` + raw `QueryWrapper0=<json>` (what the agent currently embeds via `<query>` CDATA) → the app parses it and even echoes an equivalent `qw0` into the URL bar, but **the result count never updates** (stayed at 1,141 after 7s). So `QueryWrapper0` as external input does not actually work, regardless of the `{table}`-resolution fix made earlier this session.

Gzip compression cannot be reliably generated by an LLM as text output — it must be computed in code. This means collection-page filtered search needs a new Lambda-side capability, not just a prompt fix.

**Checked whether Synapse's own REST API could do this compression for us, so the Lambda wouldn't have to reimplement it.** Cleared network logs, typed a live search into the portal's own search box, and watched what fired: the URL bar updated to `?qw0=<compressed>` immediately, and the *only* network request observed was `repo-prod.prod.sagebase.org/repo/v1/asynchronous/job/...` — the actual table-query call (same async-job pattern our Lambda's `_run_query` already uses). No separate request to any URL-shortening/query-encoding endpoint occurred. This confirms `qw0` compression is done entirely client-side in the portal's own browser JS (not a Synapse REST API capability) — there's nothing to call instead of implementing gzip ourselves; Python's stdlib `gzip` (approach below) is the correct and only path.

## Approach

### 0. Mid-implementation correction: custom SQL WHERE clauses don't work at all

While verifying the first implementation live, isolated the variable by sending the *exact* known-good SQL (`SELECT * FROM syn21897968 WHERE "datasetName" LIKE '%glioma%' OR ...`) through my own compression pipeline: it decompressed perfectly, a real Synapse query job fired (confirmed via network log and by fetching the job result directly — `queryCount: 28`, a real, valid query), but the Explore page still showed all 1,141 datasets, unfiltered.

Isolated further: sent `sql: "SELECT * FROM syn21897968"` (**no WHERE clause**) plus `additionalFilters: [{TextMatchesQueryFilter, searchExpression: "glioma"}]` — this produced "37 results filtered by glioma", exactly matching the known-good real example. Confirmed `selectedFacets` (`FacetColumnValuesRequest`) independently too: `selectedFacets: [{columnName: "species", facetValues: ["Zebrafish"]}]` → "19 results filtered by Zebrafish", matching the live facet count for that filter.

**Conclusion: the portal ignores any custom WHERE clause in `sql` and reconstructs its own query from `additionalFilters`/`selectedFacets` — `sql` is only ever the bare `SELECT * FROM {tableId}`.** This means `buildExploreUrl` cannot take a raw SQL string for filtering (revising the design in section 1 below accordingly, confirmed with the user before implementing).

### 1. New Lambda function: `buildExploreUrl` (`agents/cckp-copilot/lambda/cckpSqlRag/lambda_function.py`)

Takes a table alias + optional free-text search + optional facet filters, and returns a ready-to-use, fully-encoded portal URL — the agent just echoes it verbatim as `<target>`. No SQL WHERE clause involved at all for this path (that's what `sqlQuery`/`getColumns` etc. are for; this function is purely for building a working portal link).

- Add a `RESOURCE_PATHS` map alongside `TABLES`: `{"datasets": "Datasets", "publications": "Publications", "tools": "Tools", "grants": "Grants", "education": "Educational Resources"}` (note the literal space for education, confirmed above).
- `build_explore_url(params)`: resolve `table` → synId (reuse `_resolve_table`). Base query is always `{"sql": f"SELECT * FROM {syn_id}", "includeEntityEtag": False, "isConsistent": True}`. If `searchExpression` is given, add `additionalFilters: [{"concreteType": "org.sagebionetworks.repo.model.table.TextMatchesQueryFilter", "searchExpression": ..., "searchMode": "NATURAL_LANGUAGE"}]`. If `facets` is given (list of `{"columnName": ..., "values": [...]}`), add a `selectedFacets` entry per facet: `{"concreteType": "org.sagebionetworks.repo.model.table.FacetColumnValuesRequest", "columnName": ..., "facetValues": [...]}`. Gzip-compress with Python's stdlib `gzip`, base64-encode, URL-encode, return `{"url": f"https://cancercomplexity.synapse.org/Explore/{RESOURCE_PATHS[table]}/?qw0={encoded}"}`. Standard gzip is cross-implementation-compatible (any valid DEFLATE+gzip-container stream decompresses correctly regardless of producer), confirmed by live-testing Python-generated qw0 values directly against the portal.
- Register in `lambda_handler`'s function dispatch and `map_api_path_to_function` (e.g. `/explore-url` → `buildExploreUrl`), following the exact pattern of the 6 existing functions.

### 2. OpenAPI schema — both copies

Add the `/explore-url` operation + `BuildExploreUrlRequest`/`BuildExploreUrlResponse` schemas to **both** `agents/cckp-copilot/lambda/cckpSqlRag/openapi.yaml` (standalone reference — already has minor pre-existing drift from the embedded copy, confirmed via diff) and the `ApiSchema.Payload` block embedded in `cloudformation.sql.yaml` (the one that's actually deployed) — matching whichever wording each already has at that point, not force-syncing unrelated pre-existing drift.

- **Resource Detail Page Links table**: replace all 5 rows with the confirmed real patterns above (path segment, not query string; fix the Educational Resources collection-path space; fix Grants' key field description from "grantNumber-distinct" query param to "a synId, e.g. syn9775689" path segment).
- **Raw Synapse fallback**: fix the URL format to `https://www.synapse.org/#!Synapse:{id}` (confirmed real).
- **Collection-page filtered search**: replace the current "hand-build `<query>` CDATA with `{table}` resolved" instructions with "call `buildExploreUrl`, then use the returned `url` directly as `<target>` (no `<query>` block at all)." Remove the now-obsolete `{table}`-in-redirect warnings and worked-example XML `<query>` blocks added in earlier fixes this session — replace with a `buildExploreUrl` call + direct-URL-as-target example.
- Keep unfiltered collection redirects (`/Explore/Datasets` → now `/Explore/Datasets/`, trailing slash, no query) as a simple literal target — no Lambda call needed when there's no filter to encode.
- Re-verify the instruction stays comfortably under the max-size limit hit earlier this session (was 10,326 chars before this change; removing the old `<query>` CDATA machinery should roughly offset the new tool's addition).

### Addendum: harden against the model garbling the opaque `qw0` URL in transit

Live-usage bug, found immediately after this fix shipped: the user asked the deployed dev agent the same question twice. The first response contained a `buildExploreUrl` URL whose `qw0` value failed to decompress — decoded to 287 base64 characters (one short of a valid multiple of 4), and even after correcting the padding, the underlying bytes weren't a valid gzip stream (failed at DEFLATE decompression, not just base64). The second response, for the identical question, produced a byte-perfect, fully valid `qw0` (confirmed: correct length, valid gzip, decompresses to the exact expected `{"sql": "SELECT * FROM syn21868591", ..., "additionalFilters": [...searchExpression: "glioma"...]}`).

Since the same underlying `buildExploreUrl` call is deterministic in structure (only the gzip header's timestamp bytes vary between calls, which is harmless), and one of two identical requests came back corrupted while the other didn't, the defect isn't in the Lambda — it's in the agent's own model reproducing a ~280-character opaque, high-entropy base64 string verbatim in its generated response text. This is a known LLM failure mode: long non-linguistic strings (base64/hashes) are exactly the content models most often drop or substitute a character in when generating output tokens, since there's no true "copy" primitive at that layer.

Added an explicit instruction next to the `buildExploreUrl` toolset entry: treat its `url` as opaque and copy it character-for-character into `<target>`, never retype/reconstruct/paraphrase any part of it, since a single dropped/changed character makes the link non-functional with no visible error. This is a mitigation, not a guarantee — no prompt instruction can force byte-perfect verbatim reproduction from a language model — but it's a real, cheap, evidence-backed addition given the demonstrated failure. Instruction length after this change: 10,759 chars — still well under the pre-condensing size that caused the original max-size error. No plan-mode round was used for this one, consistent with how prior small addenda to this file were handled — no new unverified facts, a single targeted instruction addition.

### Addendum 2: `buildExploreUrl` returned an absolute URL, which broke redirects entirely

Live-usage bug reported immediately after the above: the user confirmed a byte-perfect, fully valid `qw0` URL (independently re-verified here — correct base64 padding, valid gzip, decompresses to the exact expected query shape) still didn't trigger a redirect. Root cause: `build_explore_url` returned a **full absolute URL** (`https://cancercomplexity.synapse.org/Explore/...`), but every `<target>` value that had ever worked before was a **relative path** (e.g. `/Explore/Datasets`) — including the plain Collection/Detail Page targets already in the same instructions. The chat frontend's redirect handler resolves `<target>` against its own base URL; feeding it an already-absolute URL breaks that resolution. This exactly matches the user's own timeline ("was working earlier but stopped after implementing the URL encoding/compression fixes") — it broke precisely when `buildExploreUrl` started returning absolute URLs.

Fix: changed `build_explore_url` to return a relative path (`/Explore/{path}/?qw0=...`), matching every other redirect target. Removed the now-unused `PORTAL_BASE_URL` constant. Updated the docstring, both OpenAPI response-schema descriptions (standalone + embedded), and the 3 tests that asserted on the old absolute-URL prefix; added a `test_url_is_relative_not_absolute` regression test. Full suite: 77/77 passing.

The user separately confirmed the flip side of this same distinction: links *shown to the user* in `<chat>` (markdown links to Detail Pages, and the raw-Synapse fallback) must stay absolute — a redirect `<target>` and a human-facing clickable link are two different routes for surfacing information, with different formatting rules, and shouldn't be conflated. Added an explicit rule to that effect in the "Resources: Collection & Detail Page Links" section (immediately after the table) stating both rules side by side, since the table's path values are now used in two different contexts (relative for `<target>`, absolute-with-domain-prepended for `<chat>` markdown links) and that dual use is exactly the kind of ambiguity that caused this bug. Instruction length after this addendum: 11,088 chars — still well under the pre-condensing size. Caught and immediately fixed one indentation slip of my own (a dropped leading 8-space block-scalar indent) via the standard re-parse check before finalizing — the same category of self-introduced mistake as a prior addendum in this file, now twice caught by the same verification step rather than shipped.

### Addendum 3: malformed `<actions>` closing tags — `<invoke>` leaking from tool-call syntax into the final response

Live-usage bug, captured from a real raw agent response. The model produced:

```
<chat>
Taking you to melanoma publications now.
</chat>

<actions>
<redirect>
<target>/Explore/Publications/?qw0=...</target>
</invoke>
```

— missing `</redirect>` and `</actions>` entirely, closed instead with `</invoke>`, which isn't part of this response format at all. That's Anthropic's own tool-invocation XML syntax (`<invoke name="...">...</invoke>`, used internally when the model calls `buildExploreUrl`) leaking into the user-facing output — the model conflated the XML dialect it uses to *call* a tool with the XML dialect it's supposed to *respond* in.

Initially proposed hardening against this, but the user first reported one instance where a redirect with this exact malformation still worked (suggesting the frontend may do lenient/regex-based `<target>` extraction rather than strict whole-block XML parsing) — then clarified that was a one-off exception, not the general case, and asked to implement the fix as originally proposed.

Added an explicit rule at the top of the Response Format section, right before the worked skeleton: the `<actions><redirect><target>...</target></redirect></actions>` block must always be well-formed with every tag matched by its closing tag, citing this exact production failure, and explicitly prohibiting `<invoke>`/`<parameter>`-style tool-call syntax from appearing in the final `<chat>`/`<actions>` output. Caught and fixed one more instance of my own recurring indentation slip (dropped leading 8-space block-scalar indent) via the standard re-parse check before finalizing — third time this exact mistake has been caught by that check in this file. Instruction length after this addendum: 11,559 chars — still well under the pre-condensing size. As with the verbatim-copy hardening, this is a mitigation, not a guarantee: no prompt instruction can force a language model to never blend its own internal syntaxes, but making the distinction explicit, with a concrete example of the failure, should reduce recurrence.

### Addendum 4: self-verify `buildExploreUrl`'s own output before returning it

Following the two prior addenda (both traced to the model's *handling* of an already-correct value, not to `build_explore_url` itself), the user asked whether outputs could be checked before reaching the frontend. Researched Bedrock Agents' `POST_PROCESSING` custom parser Lambda (`PromptOverrideConfiguration` with `parserMode: OVERRIDDEN`) — confirmed real and architecturally the only mechanism that sees the agent's actual final generated text before it's returned to the caller, but no confirmed example of its exact event/response contract was found (only `PRE_PROCESSING`'s contract is documented with a worked example), so implementing it blind risked breaking every agent turn. Deferred as a follow-up, not attempted here.

What *is* safe to add now: self-verification inside `build_explore_url` itself. After building `qw0`, the function decompresses/decodes its own output and confirms it round-trips to the exact `query` dict just constructed, returning `{"error": "internal error: qw0 self-verification mismatch"}` (or a decode-failure variant) instead of a URL if it doesn't. Scope is explicitly limited: every case investigated so far had the Lambda's own output already byte-correct — the actual failures were downstream, in what the model did with a correct value afterward — so this catches a *future* regression in this function's own encoding logic, not the transcription risk from Addenda 1–3. Framed accurately to the user as such, not oversold as a fix for the observed bugs.

Added two tests: `test_self_verification_catches_encoding_bug` (mocks `gzip.compress` to return a validly-gzipped but wrong payload, confirms the mismatch is caught) and `test_self_verification_passes_for_real_output` (confirms the check doesn't false-positive on real output). One implementation snag: the mock payload has to be precomputed at module import time (`_WRONG_COMPRESSED_PAYLOAD`), since `@patch("lambda_function.gzip.compress")` patches the actual `gzip` module process-wide — computing it inside the test body would recursively hit the same patch. Full suite: 79/79 passing (77 prior + 2 new).

### Addendum 5: the `sql` field is cosmetically stripped on production, not functionally required to be absent

The user compared four URLs to figure out whether `buildExploreUrl`'s output needs to differ between environments: an agent-generated URL confirmed working on staging (full shape: `sql` + `includeEntityEtag` + `isConsistent` + `additionalFilters`), two "native" URLs captured from each environment's own search-box-driven `qw0` (both missing `sql`/`includeEntityEtag`/`isConsistent` entirely — as established in Addendum-adjacent staging testing, the portal's own JS never includes those fields for a plain search), and a fourth URL the user found that supposedly "works on production" — identical to the agent's shape minus the `sql` field.

Decoding all four showed the same pattern as before, plus one new wrinkle: production's own native `qw0` uses `searchMode: "BOOLEAN"` with a proximity-operator search expression (`"glioma" @12"`) rather than staging's `NATURAL_LANGUAGE` plain string — a cosmetic difference in how each environment's own search box happens to serialize a query, not a requirement for externally-supplied `qw0` values (confirmed below).

Live-tested directly against **production** (`cancercomplexity.synapse.org`, not staging) to isolate the real cause:

- The exact "works on staging" payload (full shape, `sql` included), hard-navigated to `/Explore/Publications?qw0=...` **without** a trailing slash: 301-redirected to `/Explore/Publications`, query dropped, landed on unfiltered 4,773 results — the same trailing-slash bug already documented above, now confirmed to reproduce identically on production.
- The same payload **with** the trailing slash added: correctly loaded **"182 results filtered by glioma."** After load, the browser's address bar had rewritten itself — client-side, via the portal's own JS — to a new `qw0` with the `sql` field stripped out. That rewritten value was byte-for-byte identical to the fourth "adjusted for production" URL the user had found.
- Separately hard-navigating directly to that already-`sql`-stripped, trailing-slash-included URL produced the identical result: **182 results filtered by glioma.**

Conclusion: the `sql` field is functionally inert on production, exactly as already established for staging — the portal always reconstructs its query from `additionalFilters`/`selectedFacets` and ignores `sql` entirely. Production additionally rewrites the URL bar post-load to drop the now-unused field, which is what made the "adjusted" URL look like a distinct, required, production-specific shape. It isn't one: it's a snapshot of what the address bar looks like *after* a successful load, not a template for constructing a fresh redirect target. Using it as a standalone `<target>` would carry exactly the same risk as any other externally-sourced URL missing its trailing slash — as demonstrated above, that source URL's lack of a trailing slash would itself cause the query-dropping redirect if used as a fresh hard-navigation target rather than reached via in-app navigation.

**No change was made to `build_explore_url` or the agent `Instruction`** — the existing output (full shape, `sql` included, trailing slash always appended) already works correctly on production, confirmed by direct live testing. This closes out a plausible-looking but incorrect hypothesis (that production needs a different payload shape than staging) before it turned into unnecessary environment-branching logic in the Lambda.
